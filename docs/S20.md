# Galaxy S20+ (y2s, SM-G986B, Exynos 990)

Boot chain: stock S-Boot (unchanged) loads `boot.img` like an Android kernel.
The "kernel" is the y2s shim (`shim/`) with the xnu payload appended to it
(`tools/mkpayload.py`: kernel + ADT + boot-args); the ramdisk and dtb are the
stock ones. S-Boot did not start an image whose ramdisk was the 16 MB payload. The shim copies xnu to
RAM, builds `boot_args` and jumps to it, like iBoot.

Hardware facts used (from `~/ios-s20/live.dts`, the stock kernel's live DT):

| What | Value |
|---|---|
| Entry | EL1 (Samsung hypervisor at EL2), MMU off, x0 = DTB |
| Payload | appended to the shim image, found at the linker symbol `_end` |
| Framebuffer | 0xF1000000, 1440x3200 a8r8g8b8 (`s3cfb.bootloaderfb`) |
| GIC | `arm,cortex-a15-gic` (GIC-400): GICD 0x10101000, GICC 0x10102000 |
| Timer | 26 MHz, virtual timer PPI 11 = INTID 27 |
| xnu RAM | 0x9A000000 + 512 MiB (low bank, clear of every static carve-out) |
| CPUs | MPIDR 0x000-0x005, 0x100, 0x101; only the boot CPU is used (`cpus=1`) |

Not ported yet: SMP, Exynos UFS (so no iOS root on storage), touch, buttons,
USB, battery. The Qualcomm drivers only start with a `/y2s-ufs` ADT node,
which the S20 ADT does not have.

## Build and test (Linux laptop)

Paths assume the clone at `~/ios-s20/ios-sweet` and the stock boot.img
unpacked to `~/ios-s20/unpack/` (`dtb` and `ramdisk` are taken from there).

1. Kernel: download the `xnu-kernel` artifact of the latest green "xnu" run
   of the fork and unzip it into `xnu/out/` (gives `kernel.development.y2s`).
2. QEMU, kernel only:

   ```
   python3 tools/mkadt.py /tmp/q.adt --qemu
   python3 tools/mkpayload.py xnu/out/kernel.development.y2s /tmp/q.adt /tmp/q.bin --cmdline 'debug=0xc serial=3 cpus=1 keepsyms=1 -enable_kprintf_spam rd=md0'
   python3 tools/qemu-y2s.py /tmp/q.bin /tmp/q-run --secs 30
   ```

3. QEMU through the real shim (needs `aarch64-linux-gnu-gcc` and `mkbootimg`):

   ```
   shim/build.sh /tmp/q.bin
   python3 tools/qemu-y2s.py /tmp/q.bin /tmp/q-shim --shim shim/out/Image --secs 30
   ```

4. Phone boot.img:

   ```
   python3 tools/mkadt.py /tmp/s20.adt
   python3 tools/mkpayload.py xnu/out/kernel.development.y2s /tmp/s20.adt /tmp/s20.bin --cmdline 'debug=0xc serial=3 cpus=1 keepsyms=1 -enable_kprintf_spam'
   shim/build.sh /tmp/s20.bin
   ```

   Flash from TWRP (adb push to /sdcard fails there; /tmp works):

   ```
   adb push shim/out/y2s-boot.img /tmp/ && adb shell "dd if=/tmp/y2s-boot.img of=/dev/block/by-name/boot" && adb reboot
   ```

   Restore the stock `boot.img` from `~/ios-s20/backup/` the same way.

Expected first result: a green band at the top (first instruction of the
shim), then the red shim screen with EL/DTB/INITRD lines, then xnu's
console, ending at `Waiting on <dict>...IOMedia...` (no root device yet),
as the Redmi did at the same milestone.

## 2026-10-21: lock screen, SMP blocked by Samsung uH

- iOS lock screen reached on 1 CPU (Y2SFramebuffer presents 1125x2436
  centred, xnu 0085).
- SMP: uH (EL2) answers every PSCI call itself, hvc and smc alike:
  CPU_ON returns 0 even for the running cpu0 and a bogus target, and
  AFFINITY_INFO stays OFF. uH's RAM log (0xC1500000, 256 KiB, hashed
  messages) is readable from EL1 and gets no line for CPU_ON.
- Samsung's start_kernel always runs RKP (uh_call 0x83000200|cmd:
  GET_RO_BITMAP 0x13, GET_DBL_BITMAP 0x14, START 0x01) before smp_init.
  From the shim (MMU off, physical pointers) both GET_RO_BITMAP and
  RKP_START freeze the phone inside uH, which presumably translates its
  arguments as Linux kernel VAs. SMP would need RKP started from inside
  xnu with a Linux-like layout; parked. The probe stays in shim.c
  (smp_probe, not called).

## 2026-10-23: touch works, iOS home screen reached

- Touch (xnu 0090, bsd/dev/y2s_sects.c): sec_ts SE7 at 0x48 on HSI2C
  0x108D0000, polled via its interrupt line gpa1-0 (0x15850024 bit 0),
  400 kHz. After S-Boot the IC holds SCL/SDA low (already in the shim);
  it is freed by switching S2DOS05 LDO2 (tsp_io) off for 30 ms. The
  S2DOS05 is reached on HSI2C4 0x10590000 after selecting I2C in
  SYSREG_PERIC0+0x1014 (USI02) and muxing gpp1-0/1 (function 2).
- S2DOS05 EN (reg 0x03) reads 0x0e while LDO1/BUCK1 (panel ddi-vdd3 /
  ddr-vddr) are on: any EN write must keep bits 0/3/4 set, or the panel
  goes dark.
- Coordinates 0..4095 map to the presented 1125x2436 (top-left low,
  bottom-right high, confirmed on the phone).
- 0089 present: stretched rows built in a cached buffer, one memcpy per
  panel row (per-pixel uncached stores painted visibly).
- Result: lock screen -> swipe up -> home screen on 1 CPU, slow.

## iOS 18 track (arm64e userland on ARMv8.2), started 2026-10-24

- iOS 17+ supports only A12+ (arm64e); the iPhone XR iOS 18 cache
  (22H374) is arm64e only. S20 cores are ARMv8.2: no pointer auth.
- tools/pac-scan.py counts ARMv8.3 instructions in the cache's __text
  sections: 626M instructions, 22.25M trapping, all but ~522 (521
  FJCVTZS + 1 far LDRAA) with same-size plain equivalents.
- tools/pac-strip.py rewrites them in place (RETAB->RET, BRAA->BR,
  BLRAA->BLR, LDRAA->LDR/LDUR, PAC*/AUT*/XPAC*->NOP, PACGA->EOR).
- Still needed: xnu-11215 port of all patches; kernel emulation of
  FJCVTZS/far LDRAA; shared-region slide must apply auth rebases as
  plain pointers; no JIT (JSC emits PAC at runtime); same rewrite for
  standalone Mach-Os (dyld, launchd, daemons); code signatures of the
  rewritten files are not enforced by our kernel.
